2. TECHNOLOGY STACK (The "Enterprise Core")
Backend (Python Mandated)

    Framework: FastAPI (Python 3.11+). Chosen for native asynchronous I/O, extreme performance, automatic OpenAPI documentation, and strict type-hinting (Pydantic), which is crucial for enterprise data validation.

    Database (RDBMS): PostgreSQL 16. The only choice for complex, ACID-compliant financial/HR transactions.

    ORM & Mapping: SQLAlchemy 2.0 (Async engine) with Alembic for migrations.

    Caching & Session State: Redis (for rate-limiting, session sharing with RAG bot, and caching complex hierarchy lookups).

    Message Broker & Background Jobs: Celery + RabbitMQ (for async email notifications, report generation) and Kubernetes CronJobs (for midnight leave accruals).

Frontend (Web-Based SaaS)

    Framework: Next.js 14 (React) with App Router. Allows for fast CSR (Client-Side Rendering) for dashboards and SSR (Server-Side Rendering) for SEO-facing SaaS landing pages.

    Styling: TailwindCSS + shadcn/ui + Framer Motion. For a creative, highly intuitive, and modern UI with micro-interactions.

    State Management: Zustand (lightweight, unopinionated) + React Query (for aggressive client-side caching, pagination, and backend syncing).

Infrastructure & DevOps

    Containerization: Docker (multi-stage builds for minimal attack surface).

    Orchestration: Kubernetes (K8s) (EKS/GKE).

    Infrastructure as Code: Terraform.

    CI/CD: GitHub Actions (Lint, Test, SonarQube scan, Build, Push to Image Registry, Deploy to K8s).

3. ENTERPRISE BACKEND MAPPING & DATABASE SCHEMA

The database must be designed for Multi-Tenancy (SaaS model). Every table must have a tenant_id.

Core Entities & Relationships:

    Tenant (Company): Manages subscription limits, active status.

    User (Employee): Contains role (Admin, HR, Manager, Employee), manager_id (Self-referential foreign key for reporting hierarchy), timezone, location_id.

    LeaveType: E.g., Annual, Sick, Maternity, Unpaid, Comp-Off. Configurable per tenant. Includes rules (requires medical certificate if > 2 days).

    LeavePolicy: Defines accrual rates (e.g., 1.5 days/month), rollover limits (max 5 days carry forward to next year), pro-rata logic.

    LeaveBalance: Tracks current, accrued, used, and rolled-over balances per User per LeaveType.

    LeaveRequest: The core transactional table. Fields: start_date, end_date, duration (allows 0.5 for half days), status (Pending, Approved, Rejected, Cancelled), reason, attachment_url.

    ApprovalWorkflow: Maps custom approval chains (e.g., Employee -> Manager -> HR).

    HolidayCalendar: Geo-specific public holidays. (A user in the NY office doesn't get India public holidays).

    AuditLog: Immutable ledger of every action (Who approved what, when, from what IP).

5. EDGE CASES & OUTLIERS (The Senior Developer Foresight)

Agents: You MUST implement technical safeguards for the following scenarios.

    The Race Condition (Double Booking):

        Scenario: User has 1 day left. They open two tabs, submit two separate leave requests for 1 day at the exact same millisecond.

        Solution: Implement pessimistic locking at the database level (SELECT ... FOR UPDATE in SQLAlchemy) on the LeaveBalance row during the transaction.

    The Timezone Nightmare:

        Scenario: Employee is in Japan, Manager in San Francisco, DB in UTC. A one-day leave on Tuesday in Japan spans Monday/Tuesday in SF.

        Solution: ALL dates/times stored in Postgres as TIMESTAMP WITH TIME ZONE (UTC). The backend uses the location_id of the requester to calculate working days and deduct balances. The UI converts UTC to local time for display only.

    Retroactive Policy Changes:

        Scenario: HR changes the annual leave policy from 20 days to 15 days in October. If you just update the policy, everyone's historical balances break.

        Solution: Immutable versioning. Create a new LeavePolicy row with an effective_from date. Historic calculations reference the old policy ID.

    Leap Years & Pro-Rata Joiners:

        Scenario: Employee joins on Feb 29th, or mid-month.

        Solution: Granular daily accrual math in the backend using Python's dateutil.

    Midnight Accrual Load:

        Scenario: At Jan 1st, 00:00, the system must run rollover calculations for 500,000 employees globally across all SaaS tenants. This will crash a monolithic loop.

        Solution: K8s CronJob fires an event -> Celery Beat picks it up -> fans out to 100+ Celery worker nodes using RabbitMQ. Workers process chunks of 1,000 users asynchronously.

6. THE "FORTRESS" - ENTERPRISE SECURITY

    Multi-Tenant Data Isolation: Implement Row-Level Security (RLS) in PostgreSQL so a bug in the code can never query another company's data.

    Authentication & Authorization: OAuth2 with OIDC. Use short-lived Access Tokens (15 mins) and HTTPOnly Refresh Tokens (7 days). Implement strict RBAC (Role-Based Access Control) using Python decorators (@requires_role("manager")).

    PII & Data Encryption: Encrypt PII (Personal Identifiable Information) at rest using AES-256 (AWS KMS or HashiCorp Vault). Encrypt in transit with TLS 1.3.

    Application Security:

        Rate Limiting: Redis-based sliding window rate limit per Tenant and per IP to prevent DDoS and Brute Force.

        Input Sanitization: Pydantic models must strictly regex-validate all inputs to prevent SQLi and XSS. No raw SQL queries allowed; only ORM.

        WAF (Web Application Firewall): Setup AWS WAF/Cloudflare rules to block known malicious payloads.

8. KUBERNETES & DEVOPS BLUEPRINT

    Docker Multi-Stage Build:

        Stage 1: Build dependencies (wheels) in a heavy image.

        Stage 2: Copy only compiled binaries to a distroless/alpine Python image to minimize CVE surface area.

    K8s Health Checks:

        livenessProbe: Hits /health/live. If it fails, K8s restarts the pod.

        readinessProbe: Hits /health/ready (checks DB and Redis connection). Traffic isn't routed until this passes.

    Horizontal Pod Autoscaler (HPA):

        Scale from 3 pods to 50 pods automatically if CPU > 70% or Memory > 80%.

    Zero-Downtime Deployments:

        Rolling updates strategy. Alembic DB migrations run as a PreHook or initContainer before new code boots up. Backwards compatible schema changes only.
